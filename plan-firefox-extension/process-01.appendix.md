# P01 付録: 設定・ドメイン正規化・ルール集合

## 背景

現行の `config.Action` はアプリ、プロセス、コマンド、通知を表現できるが、Firefoxのドメイン遮断を表すデータ形を持たない。既存 `BuildPlan` は状態遷移に応じた `Plan.Actions` を生成し、macOS側が既知のアクションを実行するための互換性境界になっている。ここへ新しいブラウザアクションを混ぜると、既存のNDJSON protocol version 1 と macOS動作へ不要な影響が及ぶ。

P01では、設定を受理する層と、遮断予定ドメインを集合化する層を追加する。後続のP02はその集合を状態ファイル、liveness、dry-runへ接続するが、P01はそれらを実装しない。設定正本は常に `~/.config/tcc-local-connector/config.yml` であり、`config.yaml` という文言はその正本を指す説明上の表記として扱う。

## Why

### `ensure` に限定する理由

`ensure` は有効なルールが継続している間の望ましい状態を表す。ドメイン遮断はその状態を維持する必要があるため、`on_enter` や `on_exit` の一度限りのイベントへ置くと、遷移タイミングに依存した遮断残留や解除漏れを招く。したがって `browser.block` を `ensure` 専用として検証で拒否する。

### 既存 `Plan.Actions` と分離する理由

既存計画はmacOS側の実行アクションを表す。ブラウザ集合はFirefox拡張へ渡すポリシー入力であり、同じ配列に入れる必要がない。純粋な `BuildBrowserPolicy` として分離すれば、既存アクションの回帰を防ぎながら、集合の正規化・重複除去・並び順を独立して検証できる。

### ASCII DNSとpunycodeを採用する理由

遮断境界を文字列として一意に扱うには、設定値をDNS名に限定し、ASCII小文字化と末尾ドット除去を共通化する必要がある。URL、path、port、wildcard、IPを許すと、ドメイン境界の意味が曖昧になる。非ASCII IDNの変換器を設定検証へ持ち込まず、利用者がpunycodeを設定することで、正規化器の責務と結果を小さく保つ。

### dry-run通知をP02へ渡す理由

P01の責務は「予定集合」を決めることまでである。遮断集合を空にすること、前回集合との差分を見て通知を一度だけ合成すること、固定タイトルを付けることは状態と世代を必要とするため、P02のポリシー状態層で扱う。P01は予定集合が正規化済み・重複なし・辞書順であることだけを保証する。

## 候補比較

| 候補 | 判断 | 理由 |
|---|---|---|
| `browser.block` を既存 `Plan.Actions` に追加 | 不採用 | macOS側が既知のアクションを処理する互換性境界を壊し、既存NDJSONの意味を拡張してしまう。 |
| ルール評価の中で都度文字列比較する | 不採用 | 大文字、末尾ドット、重複、辞書順が呼出し箇所ごとに分散する。 |
| 検証時に正規化し、純粋な集合APIで和集合化する | 採用 | 不正入力を早期に拒否し、P02へ安定した予定集合を渡せる。 |
| `on_enter` / `on_exit` でも許可する | 不採用 | 継続状態ではなく遷移イベントに依存し、遮断の維持と解除の責任境界が不明確になる。 |
| IDNを実装側で自動punycode化する | 不採用 | 依存と変換規則を増やし、設定値と実際の遮断対象の対応を見えにくくする。 |
| HTTP、launchd、systemd、常駐プロセスで集合を配信する | 不採用 | 要件の接続時起動・フェイルオープン境界を越え、既存macOS動作へ新たな常駐経路を追加する。 |

## 手動確認

実装後、P01の自動ゲートに加えて次を確認する。

1. `config.example.yml` を複製した設定へ `ensure` の `browser.block` を追加し、`x.com`、`X.COM.`、`sub.x.com` を設定する。読み込み後の集合が `x.com`、`sub.x.com` の辞書順になることを確認する。
2. 同じアクションを `on_enter` に移して検証を実行し、`browser_block_requires_ensure` が出て設定が受理されないことを確認する。
3. `https://x.com`、`x.com/path`、`x.com:443`、`*.x.com`、`127.0.0.1`、空ラベル、非ASCII IDNを設定し、それぞれ `invalid_browser_domain` で拒否されることを確認する。punycode値は受理されることを別に確認する。
4. 複数の有効ルールへ同じドメインと異なるドメインを置き、`BuildBrowserPolicy` の結果が重複なし・辞書順であること、`BuildPlan` の `Actions` に `browser.block` が出ないことを確認する。
5. P02の結合時に `dry_run=true` を設定し、予定集合は保持される一方、適用集合は空で固定タイトルの通知が集合変化時に一度だけ作られることを確認する。

## 失敗時の回復

- 設定検証の失敗は設定を受理しない。利用者はエラー識別子に従って `ensure`、`domains`、ASCII punycode表記を修正し、既存の有効設定を保持する。
- 既存 `Plan.Actions` のテストが失敗した場合、`browser.block` の候補が既存 `actions` へ流れていないかを最初に確認する。既存アクションの仕様を変えて解決してはならない。
- 集合の順序や重複テストが失敗した場合、入力 `Evaluation` を破壊していないか、mapの反復順をそのまま出力していないかを確認する。
- 文書検査が失敗した場合は、`config.example.yml` と `docs/config-schema.md` の該当節だけを実装仕様へ合わせる。未追跡の `.claude/`、`PLAN.md`、`plan/`、`docs/requirements/` は復旧対象にも変更対象にも含めない。
- P02以降の状態ファイル、heartbeat、Native Messaging、Firefox拡張の失敗はP01へ機能を戻さず、適用集合を空にする後続層のフェイルオープン契約で回復する。

## 再生成条件

次のいずれかを変更した場合は、P01のcoreと付録を同じ生成元から再生成する。

- 親計画の `★ Constants` の値、単位、定数名。
- `SC-01`〜`SC-08` のうち、P01のドメイン境界、検証、集合合成、既存回帰、導入・文書に関係する内容。
- `browser.block` の公開データ形、`ensure`限定、正規化規則、拒否対象、エラー識別子。
- P02へ渡す予定集合、`dry_run`、`planned_domains`、固定通知の契約。
- Verification Contract のコマンド、合格条件、証跡形式、失敗方針。

既存の実装コードや既存ドキュメントの行が移動しただけでは、外部挙動とシンボル境界が変わらない限り再生成しない。ただし行番号表が実装着手の妨げになる場合は、coreの行番号を現状へ更新する。
